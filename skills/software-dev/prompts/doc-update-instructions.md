# 文档进度与状态更新指令（供 Cursor/Claude Agent 使用）

执行开发任务时，请**主动维护**本任务对应的计划文档（Plan 文件），使进度和状态与执行过程同步。计划文档路径会在执行提示中给出。

## 1. 计划文档结构说明

计划文档（`docs/plan-{taskId}.md`）包含以下关键部分：

- **## Execution Log**：执行日志清单，每行格式为 `- [x] 时间: 描述`（已完成）或 `- [ ] 描述`（未完成）。
- **## 沟通记录**：重要沟通与决策，可追加条目。
- **## 问题跟踪**：遇到的问题与解决方案，可追加条目。
- **## Result Summary**：完成后填写实现总结。
- 文末 **---** 后的 **meta:** 块：YAML 风格，其中 **status** 表示任务状态。

## 2. 何时更新文档

| 时机           | 建议操作 |
|----------------|----------|
| 开始执行开发   | 在 Execution Log 中勾选或追加「开发开始」等条目；如文档中有「代码实现」等步骤，可在完成某步骤时勾选对应行（将 `[ ]` 改为 `[x]` 并补全时间戳）。 |
| 完成核心实现   | 在 Execution Log 中勾选「代码实现（核心功能完成）」；在 meta 中可将 `status` 改为 `implemented`（若约定如此）。 |
| 遇到问题/决策  | 在「问题跟踪」或「沟通记录」中追加简要说明。 |
| 全部完成       | 勾选「完成验证」等剩余项；将 meta 中 `status` 设为 `implemented`；在 **Result Summary** 中填写实现总结（修改了哪些文件、实现了哪些功能）。 |

## 3. 更新格式规范

### 3.1 Execution Log 条目

- 新追加条目格式：`- [x] YYYY-MM-DDTHH:mm:ss.sssZ: 描述` 或 `- [ ] 描述`。
- 勾选已有条目：将该行的 `- [ ]` 改为 `- [x]`，并在该行中补上时间戳（可与描述同行，如 `- [x] 2026-02-28T19:00:00.000Z: 代码实现（核心功能完成）`）。
- 时间戳使用 ISO 8601 格式（如 `2026-02-28T19:00:00.000Z`）。

### 3.2 meta 中的 status

- 仅修改 meta 块中的 `status:` 行，保持其它行不变。
- 常用取值：`planning`（规划中）、`implemented`（已实现）、若项目有约定也可使用 `testing`、`done` 等。

### 3.3 沟通记录 / 问题跟踪

- 在对应二级标题下追加内容，保持 Markdown 格式（列表或短段落均可）。

### 3.4 Result Summary

- 任务全部完成后，在 **Result Summary** 下填写一段实现总结：涉及的文件、主要改动、实现的功能要点。

## 4. 操作方式

- **直接编辑计划文档文件**：在项目仓库中打开并修改 `docs/plan-{taskId}.md`，按上述格式增删或勾选内容。
- 不要删除或破坏文档中的 **Overview**、**meta** 块整体结构；仅更新 Execution Log、沟通记录、问题跟踪、Result Summary 以及 meta 中的 `status`/`updatedAt` 等字段。

遵循以上约定，即可在开发过程中自动维护文档进度与状态，便于追踪和验收。
